# 项目产物与角色动作

只读本次角色需要的部分。先复用项目已有目录和等价文件；无约定时可集中使用 `docs/workflow/`。以下字段由主控/调度者维护，不交给用户填表；模板本身不是执行授权。

## planner：版本化计划

先核对项目身份与当前规则。小任务简写；复杂任务补接口、失败路径、集成与资源所有权。用户已明确批准的范围不重复索取批准；未批准部分保持待定，不把模板或日期当成授权。

```markdown
# 阶段计划 plan-v1
项目根：待绑定绝对路径
目标：待用户指定
版本身份：计划文件哈希或受控提交
授权：记录已有效的用户指令、范围与时间；未覆盖部分明确待决
禁止项/停止点：按当前用户授权填写，不擅自填固定次数或费用
调度者：待绑定 DSH Lead 原会话链接
审查者：Codex；业务/发布确认人另按项目要求填写

| 包ID | 交付目标 | 验收条件（可观察事实） | 依赖/接口 | 允许修改/共享资源 | 验证与回退要求 |
|---|---|---|---|---|---|
| P01 | 待填写 | 待填写 | 待填写 | 待填写 | 待填写 |

集成门：涉及接口连接时，指定集成人员、场景、失败路径和版本组合。
后续任务池：只列本次授权覆盖的任务及推进条件；其余列为建议。
```

关键设计未定时先列为待决项，不能把设计选择转嫁成执行者猜测。DSH 可建议重拆包，但不能删减目标、验收条件或权限；改变这些内容须由有权者发布新计划版本，并明确影响哪些包。

## dispatcher：当前状态与 brief

主控在调度前初始化项目/会话绑定，之后由唯一调度者维护执行状态；主控交独立验收结论供它合并，不同时改写任务表。写前重读避免覆盖并发变更。状态是快照，不替代计划中的授权。

```markdown
# 当前状态
项目根 / 当前计划与版本身份：待绑定
当前调度者 / DSH Lead 链接：待绑定
Codex 主控链接 / 本次派发 request-id / watch 注册状态：主控自动记录
验收窗口及负责包：待绑定
角色交接：未开始；不从摘要推断团队接管

| 包ID | 执行状态 | 验收结论 | owner/原会话或成员target | 交付版与证据 | 依赖/下一步 |
|---|---|---|---|---|---|
| P01 | 未派发 | 未验收 | 待绑定 | 无 | 待核实授权和前置门 |

重要未决 / 当前有效权限 / 宿主运行事实：只写影响下一步的内容。
```

执行摘要：`未派发 → 执行中 → 待验收`；缺信息、环境或授权时转为 `阻塞`，补齐后由原调度者决定恢复。
验收结论独立记录：`未验收 / 通过 / 限定通过 / 需补正 / 阻塞`。`需补正` 后由调度者安排新修订，再进入待验收。
这是项目文档状态，不要求原生 Team 工具接受同名枚举。原生任务的 pending/in_progress/completed 等按实际接口使用；completed 只映射执行结束，不能自动映射验收通过。
需要取消时保留取消事实和在途结果，先核对执行停止情况，不把“已请求取消”当成已经停止。

brief 至少包含：

```markdown
# P01 / r1 brief
角色：executor；用户批准的调度者为唯一任务来源
项目根：待绑定
计划：版本、路径与身份；验收条件引用原文或精确条目
目标与输入：自包含到足以执行，不复制完整旧聊天
独占修改范围 / 接口与共享资源 owner：待填写
依赖与前置门：明确已验收、临时依赖或待决；不能用一律“已完成”掩盖
基线与回退：任务前 dirty 摘要、原件/补丁/隔离位置、仅本包的恢复步骤
必载技能：准确名称、用途、实际可用路径；缺项的处理方式
验证：命令/cwd、必要成功与失败路径、真实外部调用权限；未授权真实调用不运行
交付：五字段摘要，绑定产物身份、证据与未执行项
停止点：范围扩大、关键接口未定、权限缺失、持续相同失败等按本包实际填写
```

一个原生 Team 成员 target 只在原 Team 内使用，不能当作 CodexHost 顶层 Thread ID。Team 内调度使用原生成员/任务工具；顶层会话通信使用 CodexHost 当前 CLI。不要混用两套标识或在两边重复建立同一执行任务。

## executor：一个回执示例

以下示例说明“通过测试但缺少必需条件”如何回报；不是实际测试结果。

```text
状态: NEEDS_CONTEXT；P01/r1；计划 plan-v1 / 已记录的文件身份
改动: src/example.py:20；任务前原件与交付哈希见 P01/evidence.md
证据: 项目根运行 pytest tests/test_example.py；期望成功与超时路径均有证据；实际成功路径通过，真实超时环境不可用
未做/风险: 计划要求的超时路径尚未验证，不能宣称本包完成
待决: 调度者确认能否用隔离故障夹具满足原条件，或提供所需环境
```

已知本包必需工作尚未完成而且能够继续时，继续修复；不能用 NEEDS_CONTEXT/BLOCKED 包装普通中途进度。缺少环境或明确事实才报对应状态。DONE_WITH_CONCERNS 仅适用于必需条件已满足、剩余问题确实不阻断交付。

## reviewer：分包与集成验收

主控从状态、DSH 回报和实际产物取得包ID、原计划身份、基线、交付版和证据入口；先核对它们互相匹配，不要求用户搬运内部字段。保持审查上下文聚焦，不默认阅读实现过程聊天，但可按问题读取源码、调用方、Diff 和原始日志；只有实际使用独立上下文时才这样声明。

```markdown
# P01 / r1 验收
结论：通过 / 限定通过 / 需补正 / 阻塞
审查身份：本轮是否作者；是否独立上下文；本次实际读取的输入
计划 / 基线 / 交付版 / 验证版：逐项绑定
条件核对：每条验收条件 → 实际证据、检查与结论
阻断问题：事实、影响、定位；交回 DSH 调度者，不直接给成员重派
可登记问题 / 未检查项：明确影响和限制
集成结论：未涉及 / 待集成 / 对指定版本组合检查的结果
```

无需为同一通过版本反复运行同样检查；新增修订、失败或风险只复查受影响部分。若验收者需要修改交付物，先声明作者角色变化，该部分不能再自称独立验收。
分包通过后，按计划执行必要的集成检查与阶段总核对。业务、真实 API 效果、生产发布等只在已批准且有对应证据时确认。

## 重要决定与恢复

重要决策记录只追加一行或一个短条目：`时间 | 决定者/批准来源 | 决定 | 原因 | 影响的计划/包`。普通进度不追加决策；发现旧决定失效时追加替代关系，不改历史使旧行为看似获准。

恢复顺序：读取当前状态 → 核对宿主、原会话/成员、在途进程和交付文件 → 判断运行中、未知、已提交或确实失败 → 在原授权内继续，或报告需要的具体决策。未知状态先对账，不能自动重派。
Codex 新审查窗口只带负责包的原计划、状态定位和证据入口；不复制全段历史。保持原 DSH Lead，避免双调度者。
